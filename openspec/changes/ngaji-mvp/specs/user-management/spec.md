## ADDED Requirements

### Requirement: One user, one group, one role
Each user SHALL have exactly one `UserGroupRole (groupId, role)`. Users SHALL never be deleted; `isActive` controls access.

#### Scenario: Deactivate instead of delete
- **WHEN** an OWNER "removes" a user
- **THEN** `isActive` is set to false and the row remains

### Requirement: Create users
OWNER and ADMIN SHALL create USER or ADMIN accounts for any group in scope. Only OWNER SHALL create OWNER accounts. Usernames SHALL be unique. The initial password SHALL be generated by the server, shown exactly once, never logged, and the account SHALL have `mustChangePassword = true`.

#### Scenario: ADMIN creates ADMIN in child group
- **WHEN** an ADMIN at daerah D creates an ADMIN for kelompok K under D
- **THEN** the account is created and `user.create` is audited without the password

#### Scenario: ADMIN cannot create OWNER
- **WHEN** an ADMIN submits role OWNER
- **THEN** the system responds 403

### Requirement: Change role, move group, activate/deactivate
Only OWNER SHALL change a user's role, move a user to another group in scope, or toggle `isActive`, subject to the self-protection rules in `authorization`.

#### Scenario: Move to group outside scope
- **WHEN** an OWNER at daerah D moves a user to a group under another daerah
- **THEN** the system responds 404

### Requirement: Reset password policy
OWNER SHALL reset the password of any user whose group is in scope (including other OWNERs and child groups). ADMIN SHALL reset only users with role USER whose `groupId` equals the ADMIN's own `groupId`. A reset SHALL set a server-generated temporary password, set `mustChangePassword = true`, and audit `user.reset_password` without the password.

#### Scenario: ADMIN resets USER in same group
- **WHEN** an ADMIN at kelompok K resets a USER at K
- **THEN** the reset proceeds

#### Scenario: ADMIN cannot reset peer ADMIN
- **WHEN** an ADMIN at K resets another ADMIN at K
- **THEN** the system responds 403

#### Scenario: ADMIN cannot reset USER in child group
- **WHEN** an ADMIN at daerah D resets a USER at kelompok K under D
- **THEN** the system responds 403

#### Scenario: OWNER resets in child group
- **WHEN** an OWNER at D resets an ADMIN at K under D
- **THEN** the reset proceeds

### Requirement: User management page
`/pengguna` SHALL list users in scope and expose only the controls the caller is allowed to use; the Server Actions SHALL enforce the same rules independently of the UI.

#### Scenario: Hidden control still enforced
- **WHEN** an ADMIN crafts a request to reset an OWNER's password
- **THEN** the system responds 403 even though no button was shown
