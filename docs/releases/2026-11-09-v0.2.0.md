## 1. Summary

Every member gets a permanent code (`ANR-7K3MQ9`) shown on the member page and searchable in the member list. Admins can record family relations (parent, guardian, spouse, sibling) on the member page, including across kelompok; people outside the viewer's scope appear as plain text only. Existing members get their codes from a one-off backfill that **must be run right after the new container is up**. OpenSpec change: `openspec/changes/member-relations-and-codes/`; design in DESIGN.md §14.

## 2. Changes

**Added**
- `Member.code` (`PREFIX-XXXXXX`, unique) and `Organization.memberCodePrefix` (2–4 letters A–Z, unique, permanent).
- Codes assigned on member creation and CSV import; a client-supplied code is ignored.
- Search by code in the member list (case and dash insensitive) and a hidden-by-default "Kode" column.
- `MemberRelation` and the Keluarga section on the member Profil tab (add, remove, plain-text display for out-of-scope relatives); `member.relate` permission and audit actions `member.relate`, `member.unrelate`, `member.code_backfill`.
- `pnpm member-codes:backfill <orgId>=<PREFIX> ...` (idempotent, audited).
- `BOOTSTRAP_MEMBER_CODE_PREFIX` is now required by `pnpm org:create`.

**Changed**
- Keluarga card layout and tab strip underline (no stray vertical scrollbar); "+N lagi" label on the activity calendar exempted from the 14px rule.
- Also in this branch: the `member-group-move` OpenSpec change documents (proposal, design, specs, tasks only; no code) and `AGENTS.md` (written by `next dev`).

## 3. Risk and impact

- **Migrations:** `prisma/migrations/20261107120000_member_relations_and_codes`. Adds two nullable columns, one new table and three unique indexes. Nothing is dropped or rewritten, so older code ignores it. Reversible only by restoring a backup or snapshot.
- **Config / env changes:** none for the running app. `BOOTSTRAP_MEMBER_CODE_PREFIX` matters only when creating a new organization.
- **Data impact:** the backfill writes a code for every existing member and sets each organization's prefix. **Prefixes are permanent.** Until it runs, creating a member fails with a generic error (it never creates a code-less member); viewing and everything else works.
- **Downtime:** a few seconds while the container is replaced.
- **Sessions:** no re-login needed.
- **Dependency audit exceptions:** none new (re-check DEPLOYMENT.md §5 at deploy time).

## 5. Deploy steps (Docker)

Steps 1–4 of DEPLOYMENT.md §9 (backup, snapshot, send the code with `<ref>` = `v0.2.0`, audit gate), then:

```bash
cd /opt/dahan
sudo docker compose up -d --build
sudo docker compose logs --tail 30 app     # "migrations ... applied", then "Ready"
```

Then, **immediately**, the backfill (one `<organizationId>=<PREFIX>` per organization; fill in before deploy):

```bash
# TODO before deploy: replace with the real ids and prefixes
sudo docker compose exec -T app pnpm member-codes:backfill 1=<PREFIX> 2=<PREFIX>
```

| Organization ID | Name | Prefix |
|---|---|---|
| `<id>` | `<name>` | `<PREFIX>` |

It refuses, changing nothing, if an organization would stay without a prefix or an existing prefix would change. Running it twice is safe (second run changes nothing).

```bash
curl -I https://dahan.ilyasmustafa.com/login
sudo sqlite3 /var/lib/dahan/production.db "SELECT count(*) FROM Member WHERE code IS NULL"   # must print 0
sudo sqlite3 /var/lib/dahan/production.db "SELECT id, memberCodePrefix FROM Organization"    # every row has a prefix
```

After a successful upgrade: `sudo docker image prune -f`.

## 7. Rollback

1. App-only problem, backfill not run: send the previous tag the same way (DEPLOYMENT.md §4) and `sudo docker compose up -d --build`. The new columns and table are ignored by older code.
2. Backfill run or data damaged: restore the `pre-v0.2.0` VPS snapshot, or run `scripts/restore.sh` with the pre-upgrade backup (DEPLOYMENT-DOCKER.md "Operating": stop the container, run with `SKIP_SERVICE=1`, start again), and redeploy the previous tag. Codes written by the backfill are lost with the restore; running it again later reproduces valid codes but **different random values**, so do not share codes with users before this release is settled.
3. Record what happened in section 8 and set Status to `Rolled back`.
